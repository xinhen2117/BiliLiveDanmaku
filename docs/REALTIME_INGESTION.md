# 实时弹幕的接收边界与实现

本客户端的目标是尽可能完整处理**服务端实际推送到当前连接的普通弹幕**，不是保证取得直播间所有消息的归档服务。登录、认证成功、Brotli 或更大的缓冲都不能证明服务端推送了全部消息；断网和重连期间的缺口没有补拉保证。

## 常见弹幕姬的工作链路

1. 将短房间号解析为真实房间号，并获取弹幕 token 与服务器列表。
2. 建立 WebSocket，发送包含房间、UID、buvid、token、协议版本等字段的认证包。收到成功的认证回复后才进入已连接状态。
3. 定期发送心跳，区分心跳回应、认证回应与业务消息。连接中断后退避重连，重新获取配置；服务器列表可以轮换，但不以无 token 连接、随机身份或切换账号绕过认证/风控拒绝。
4. 按包头长度遍历粘包，根据版本处理普通 JSON、zlib 或 Brotli；一帧可以包含很多弹幕，不能把 WebSocket 一次回调当成一条消息。
5. 识别普通弹幕命令与新旧正文结构，再送入有界存储和界面。关键词过滤、重复折叠、历史保留数量属于展示策略，不是网络接收结果。

来源为上游原始源码，不是 Bilibili 对第三方客户端的稳定性保证：

- [blivedm WebSocket 基类，固定提交](https://github.com/xfgryujk/blivedm/blob/3bf17fe862b8c2fc6bc04c81c3f0c5db95de93d6/blivedm/clients/ws_base.py)：认证、心跳和重连处理。

## 本次消除的本地漏收点

旧传输层对每条解析出的消息执行 `Channel.BUFFERED.trySend`，没有检查结果。合成的单帧 200 条消息在普通测试调度下只能交付 65 条，其余没有诊断。现在采用按帧拆分的有界批次队列，成功入队的消息保持顺序；不会按内容去重。合成的普通粘包、zlib 和 Brotli 突发均覆盖了 200 条接收回归。

- 解码与连接会话运行在后台 dispatcher，解压和 JSON 解析不占 UI Main，也不在 OkHttp 回调中等待消费者。
- 待交付数据同时限制为 64 批、8192 条与约 8 MiB 的 UTF-16 字符串/对象预算。每批最多 256 条；正在交付、尚未释放的消息仍计入预算。该估算不是精确堆内存测量，另有对象数量上限。
- 原始帧另有 64 个事件、8 MiB 待处理字节预算，单帧不超过 4 MiB。回调在复制帧前预留预算，不能无限创建挂起发送任务。
- 下游消费者变慢不会挂住心跳。定时 tick 使用独立的合并通道，优先检查单调时钟截止时间；回调仅扫描包头记录心跳回应到达时间，不解压、不解析 JSON，以免及时到达的回应因解析排队被误判为超时。
- 队列满时不静默吞掉结果。已解码消息按“条”计数，解码前丢弃只按“帧”计数，因为无法知道帧里有多少弹幕。解码后超限保持连接和心跳；原始队列超限结束该连接并按自动重连设置处理。主动换房/断开不会把取消的旧房间消息冒充溢出。
- 换房时清空旧队列，迟到回调与队列消息受会话代际隔离；消费者取消不会丢掉整批尚未取出的尾部。

旧显示层在界面隐藏时仍只攒 512 条待发布消息，历史配置即使允许 1000 条也会提前淘汰。现在每条合格消息立即更新有界历史和折叠状态，UI 快照独立发布。后台不建立重绘定时器，回到前台发布一次当前快照，正常 50 ms / 低功耗 250 ms 合批不变。

## 协议与连接兼容性

- 宣告 protover=3，保留普通 JSON、zlib=2 和 Brotli=3 解码。
- 支持 `DANMU_MSG`、`DANMU_MSG_MIRROR` 及命令后缀，兼容旧 info 和 dm_v2-only。有效 dm_v2 优先；损坏时仅在旧 info 本身有效的情况下回退，不输出一条消息的两个副本。
- dm_v2 解码限制长度、字段数量、varint 和 UTF-8。UID 使用 64 位范围检查；超出本项目有符号 Long 表达能力时保留正文并标未知身份，不截断或拿旧 UID 冒充。
- 保留配置返回的多个服务器，按重连尝试轮换。仅连接有效端口的 HTTPS Bilibili 域名，不把 token/Cookie 传到任意返回域，不使用无 token 公共服务器兜底。
- 自动重连开启时，明确认证拒绝仅允许一次重新发现/获取凭据并重试；再次拒绝停止。关闭自动重连时不进行这次重试。不会自动重新登录、短信验证或绕过风控。
- 本次仍使用现有 `room_init` 与 `getConf` 发现接口。上游 `getDanmuInfo` / WBI 发现流程**尚未迁移**，没有据此断言旧接口失效或线上已验证。

## 诊断的单位

界面分别展示接收丢弃条数、未解析丢帧、过滤条数、折叠条数、历史淘汰行数及超大显示拒绝条数。折叠的一行可能代表多条消息，不能将“淘汰行”换算为“网络丢弹幕”。

- 传输计数在一次显式连接/换房时清零，自动重连继续累计；清屏不抹去传输诊断。
- 展示计数随清屏重置；正常历史滚动、过滤和折叠不算传输失败。
- 不支持的业务命令（礼物、SC、互动等）不计作丢失普通弹幕。
- 已有的帧/解压/JSON 安全上限继续生效。格式错误、不受支持或超出解析预算的内容可能不输出；传输诊断并非对服务端全部消息的审计或补拉机制。

## 验证范围

本地回归只使用虚构数据和本地 MockWebServer，覆盖压缩突发、慢消费者、心跳/认证、预算溢出、取消、房间切换、dm_v2 边界和后台历史。完整 Android 单元测试、Lint、Debug APK 和仪器测试 APK 编译应以该提交的 CI 为准；编译仪器测试不等于在设备上运行。没有使用真实 Bilibili 登录、Cookie、手机号或房间消息，未声称通过线上、真机或功耗验证。
